Step 8. Enter the pipeline code
Your lab manual provides the following structure. We will use a corrected version that is suitable for Windows and avoids repeatedly cloning into an existing directory.

pipeline {
    agent any

    tools {
        maven 'MAVEN-HOME'
    }

    stages {

        stage('git repo & clean') {
            steps {
                bat 'git clone https://github.com/kabrakanak26-pixel/Week4-Maven-Lab.git mavenjava'
                bat 'mvn clean -f mavenjava/pom.xml'
            }
        }

        stage('install') {
            steps {
                bat 'mvn install -f mavenjava/pom.xml'
            }
        }

        stage('test') {
            steps {
                bat 'mvn test -f mavenjava/pom.xml'
            }
        }

        stage('package') {
            steps {
                bat 'mvn package -f mavenjava/pom.xml'
            }
        }
    }
}



A note about the repository: This uses the Week4-Maven-Lab GitHub repository from your earlier Jenkins practical. The script assumes that the repository contains a pom.xml at its root. If your repository has a different structure, the Maven POM path must be adjusted.

Also, the clone command creates a fresh mavenjava directory. Jenkins normally uses the same workspace between builds, so we will address cleaning that directory in the troubleshooting section.
Step 9. Understand every part of the script
Let's understand the code because your professor may ask you to explain it.
1. Pipeline declaration
pipeline {


This declares the beginning of a Jenkins Declarative Pipeline.
2. Agent
agent any


This tells Jenkins to execute the pipeline on any available agent.

An agent is the machine or node that executes the pipeline.
3. Tools
tools {
    maven 'MAVEN-HOME'
}


This tells Jenkins to use the Maven installation registered under the name MAVEN-HOME.
4. Stages
stages {


This contains all the stages of our pipeline.
5. Git repository and clean
stage('git repo & clean') {
    steps {
        bat 'git clone REPOSITORY_URL'
        bat 'mvn clean -f mavenjava/pom.xml'
    }
}


- git clone downloads the source code.
- mvn clean removes previous build output, typically the target directory.
- bat executes Windows Command Prompt commands.
6. Install
stage('install') {
    steps {
        bat 'mvn install -f mavenjava/pom.xml'
    }
}


This executes the Maven install lifecycle.

It compiles the source, runs tests and packages the project as required by the Maven lifecycle, then installs the artifact in the local Maven repository if successful.
7. Test
stage('test') {
    steps {
        bat 'mvn test -f mavenjava/pom.xml'
    }
}


This executes the test cases defined in the Maven project.

If tests fail, the pipeline normally stops.
8. Package
stage('package') {
    steps {
        bat 'mvn package -f mavenjava/pom.xml'
    }
}


This generates the final application artifact.

Depending on the project's packaging type, it generates:
- .jar – Java application.
- .war – Java web application.
9. Closing braces
    }
}


These close the stages and pipeline blocks.

One important technical detail: mvn install already performs earlier lifecycle phases, including test and package. Therefore, the separate test and package stages execute those phases again. This is how your lab manual is structured, so we'll retain it for the experiment.
Step 10. Make the script work for repeated builds
There is one issue you should understand before running it.

Suppose your first build creates:
workspace/
    mavenjava/


When you run the second build, Git tries to clone into the same folder. It may fail because the directory already exists.

To prevent this, use Jenkins' deleteDir() command before cloning.

Replace the previous script with this final version:

pipeline {
    agent any

    tools {
        maven 'MAVEN-HOME'
    }

    stages {

        stage('git repo & clean') {
            steps {
                deleteDir()

                bat 'git clone https://github.com/kabrakanak26-pixel/Week4-Maven-Lab.git mavenjava'

                bat 'mvn clean -f mavenjava/pom.xml'
            }
        }

        stage('install') {
            steps {
                bat 'mvn install -f mavenjava/pom.xml'
            }
        }

        stage('test') {
            steps {
                bat 'mvn test -f mavenjava/pom.xml'
            }
        }

        stage('package') {
            steps {
                bat 'mvn package -f mavenjava/pom.xml'
            }
        }
    }
}



Here is the difference:
Command	Purpose
deleteDir()	Deletes the existing Jenkins workspace contents.
git clone	Downloads a fresh copy of the repository.
mvn clean	Cleans the Maven project's previous build output.

deleteDir() is a Jenkins Pipeline step, whereas mvn clean is a Maven command. They are not the same thing.

Before running: Confirm that your repository is accessible and contains pom.xml at its root. If the project is inside a subfolder, adjust the POM path accordingly.

cocktailmake.github.io


C. GitHub Webhook – Trigger on a push
This is different from Poll SCM.

A webhook sends a notification from GitHub to Jenkins whenever an event such as a push occurs.

Steps:
1. Open your Jenkins job.
2. Click Configure.
3. Under Build Triggers, select GitHub hook trigger for GITScm polling.
4. Save the job.
5. Open your GitHub repository.
6. Go to Settings → Webhooks.
7. Click Add webhook.
8. Enter your publicly reachable Jenkins webhook URL:
http://YOUR_PUBLIC_JENKINS_URL/github-webhook/


9. Select application/json.
10. Select the push event.
11. Click Add webhook.








medium.com


Important: Your local address localhost:8080 is not accessible to GitHub's servers. A GitHub webhook requires a publicly reachable Jenkins endpoint or an appropriate secure tunnel. Don't expose Jenkins directly without securing it.

For your local college practical, Poll SCM is the simpler option.
